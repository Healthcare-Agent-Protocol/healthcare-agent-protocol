Healthcare Agent Protocol (HAP) defines a proposed way for healthcare agents to discover operations, establish access, and exchange structured results.

<Warning>
  HAP is an early design draft. The protocol, reference implementation, and conformance suite are not complete.
</Warning>

## Start with a business operation

A provider or RCM agent should be able to request claim status using a shared contract.
The agent first discovers the payer's credential requirements.
The payer or an approved intermediary verifies identity and provider delegation, then issues a verifiable digital credential (VDC).
The payer validates that VDC and enforces its record limits.
The result should state the claim status, its source, and when the payer observed it.

The first proposed pilot supports claim-status reading under the scope `claim.status.read`.
The [claim-status operation](/spec/claims/claim-status) defines request and response schemas and its A2A 1.0 messages.
It covers payment tracing, denial details, pending requirements, service lines, review instructions, remittance, and follow-up references.

## Authenticate before a phone call

The agent reads a payer-published JSON card or authenticated configuration to discover where to register.
It makes an authenticated API request before dialing and gets a call reference plus correlation instructions.
The payer can host that service or select Pindrop or another verifier; these are proposed roles, not claims of vendor support.
The agent carries the correlation through a negotiated method such as DTMF or spoken digits.
The payer verifies it through a lookup or gets an authenticated result through its verifier integration.

A positive call result establishes identity and call correlation. Protected access still needs the accepted VDC and payer authorization.
Read the [pre-call authentication proposal](/spec/identity/hap-1-voice) for discovery, registration, and both verification paths.

## Keep clear boundaries

- A payer-accepted VDC is required for every protected delegated RCM operation.
- Trusted intermediaries are optional at the protocol level. Each payer can require one, issue VDCs directly, or accept both paths.
- Payer-led discovery tells the client which issuers and acquisition methods are accepted.
- Voice discovery selects the registration service and call-correlation methods; a call reference does not replace an access VDC.
- An approved intermediary issues its VDC directly; the payer does not issue a replacement for that path.
- The payer enforces VDC scope, key binding, record permissions, and local access policy in both paths.
- Claim data passes directly between client and payer.
- Payload encryption is an optional privacy pattern. Transport security and verified delegation remain required.
- A completed lookup can report a claim that remains pending.

## Build on existing standards

[UCP](https://ucp.dev/specification/overview/) inspires the organization of capabilities, versions, extensions, and transport bindings.
[A2A](https://a2a-protocol.org/latest/specification/) is a proposed transport for agent tasks and results.
The HAP-1 identity core also supports deployments without A2A.

X12 005010 transactions, FHIR resources, and payer APIs can support integrations behind the business contracts.
This project does not claim affiliation with UCP or A2A, industry endorsement, or production readiness.
